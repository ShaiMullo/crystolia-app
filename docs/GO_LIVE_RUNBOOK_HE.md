# ספר תפעול — הפעלה מסחרית של Crystolia

מסמך זה מיועד לבעל העסק ולמי שמתפעל את המערכת ביום-יום. הוא מניח שהקוד כבר פרוס ושמסך **אדמין ← מערכת ← מוכנות להפעלה** זמין. כל פעולה שמסומנת 🔑 דורשת החלטה או נתונים שרק בעל העסק מחזיק.

---

## 1. רשימת בדיקה לפני השקה

עוברים על מסך **מוכנות להפעלה** (אדמין ← מערכת ← מוכנות להפעלה) ומוודאים:

- [ ] **טרנזקציות MongoDB** — ירוק (topology: replica_set). אם אדום — אין לאשר הזמנות; ראו סעיף 11.
- [ ] **אינדקס חשבונית-להזמנה** — ירוק.
- [ ] 🔑 **העברה בנקאית** — הוזנו פרטי החשבון **האמיתיים** (סעיף 2).
- [ ] **כרטיס אשראי** — מוצג "לא זמין" (תקין! אין ספק סליקה מחובר; הלקוחות לא רואים אפשרות זו).
- [ ] 🔑 **מלאי** — לכל המוצרים במעקב יש מלאי פתיחה זמין (סעיף 4).
- [ ] דוא"ל / SMS — במסך המוכנות שימו לב להבחנה: **"מוגדר"** = קיימים מפתחות; **"מאומת"** = הוכח שעובד; **"נבדק בהצלחה"** = שלחתם הודעת בדיקה אמיתית וקיבלתם אותה. לפני השקה יש להגיע לפחות ל"נבדק בהצלחה" פעם אחת (סעיף 5).
- [ ] בוצעה הזמנת בדיקה מבוקרת מקצה לקצה (סעיף 5).
- [ ] גיבוי אחרון תקין (סעיף 7).

## 2. 🔑 הזנת פרטי בנק אמיתיים

1. אדמין ← הגדרות ← אמצעי תשלום ללקוחות.
2. מסמנים "אפשר תשלום בהעברה בנקאית" וממלאים: שם בנק, סניף, מספר חשבון, שם בעל החשבון, IBAN (**חובה**), ואופציונלית SWIFT/BIC וכתובת הבנק (להעברות מחו"ל).
3. שומרים. המערכת מאמתת את ה-IBAN (בדיקת ISO 13616) ומצליבה אותו מול הסניף ומספר החשבון — שמירה עם פרטים לא עקביים תידחה עם הסבר מדויק. ה-IBAN וה-SWIFT נשמרים מנורמלים (אותיות גדולות, בלי רווחים).
4. **חשוב:** הפרטים האלה נשלחים ללקוחות במייל אישור ההזמנה ומוצגים באזור העסקי — לוודא שהם זהים למסמך הרשמי מהבנק.
5. הערכים הקיימים היום הם שאריות מההדגמה — חובה להחליפם לפני הזמנה אמיתית ראשונה.

## 3. כיבוי כרטיס אשראי עד לחיבור ספק

גם כשהדגל "אפשר תשלום בכרטיס" דלוק — הלקוחות **לא** רואים אפשרות אשראי ואישור הזמנת-אשראי חסום, כי אין ספק סליקה מאומת. ובכל זאת, לסדר מומלץ:

1. אדמין ← הגדרות ← לבטל את הסימון "אפשר תשלום בכרטיס אשראי" ולשמור.
2. המערכת תדחה כל ניסיון לשמור את קישור עמוד הדמו כספק.
3. אחרי הכיבוי אפשר לבקש הפעלה של `DEMO_PAYMENT_PAGES_DISABLED=true` בקובץ `deploy/demo/.env.demo` שבשרת (מכבה סופית את עמודי הדמו — פעולת תשתית, לא מהאדמין).

## 4. 🔑 מלאי פתיחה

1. אדמין ← מלאי.
2. לכל מוצר במעקב: תנועת **"כניסה" (in)** עם הכמות הנקלטת — זו קבלה מצטברת שמתועדת ביומן התנועות, והדרך הרגילה להוסיף מלאי.
3. **"התאמה" (adjustment) קובעת ערך מוחלט** של הכמות במלאי — היא מיועדת אך ורק לתיקון אחרי ספירת מלאי פיזית, והיא מתועדת ככזו ביומן. אל תשתמשו בה להוספה שוטפת.
4. מוצר שלא רוצים לנהל לו מלאי (למשל שירות): אדמין ← מוצרים ← לכבות "מעקב מלאי" עבורו.
5. שימו לב: **אישור הזמנה נכשל בכוונה** כשאין מלאי זמין מספיק — ההודעה תציין את המק"ט החסר.

## 5. הזמנת בדיקה מבוקרת (מקצה לקצה)

מומלץ פעם אחת לפני השקה, עם לקוח בדיקה אמיתי-למראה:

1. **הרשמה:** להירשם בפורטל העסקי עם כתובת מייל שבשליטתכם ← לאשר את ההרשמה באדמין.
2. **הזמנה:** להתחבר כלקוח, להזמין כמות קטנה (למשל ארגז אחד), לבחור העברה בנקאית.
3. **אישור:** באדמין ← הזמנות ← לאשר. לוודא: הסטטוס עבר ל"מאושרת", נוצרה חשבונית טיוטה, המלאי המשוריין גדל בהתאם (אדמין ← מלאי).
4. **עדכוני לקוח:** לוודא שהגיע מייל אישור עם פרטי ההעברה הבנקאית (ו-SMS אם מוגדר). אם נכשל — כפתור "שליחה חוזרת של עדכון ללקוח" בעמוד ההזמנה.
5. **משלוח:** לעדכן ל"נשלחה" ← המלאי הזמין יורד והשריון משתחרר; ואז "הושלמה".
6. **ניקוי:** את הזמנת הבדיקה אפשר להשאיר (היסטוריה לגיטימית) או לבטל — לא למחוק רשומות ידנית מה-DB.

## 6. אימות עדכוני דוא"ל/SMS

- כל שליחה נרשמת בציר-הזמן של ההזמנה (נשלח/נכשל לכל ערוץ).
- נכשל? כפתור **שליחה חוזרת** בעמוד ההזמנה. המערכת שולחת מחדש **רק את הערוץ שנכשל** (מייל שנשלח בהצלחה לא יישלח שוב), חוסמת לחיצה כפולה, ומתעדת הכול ביומן הביקורת.
- **חשוב לדעת:** אם תהליך קרס באמצע שליחה, התוצאה תסומן "לא ידוע" — במצב כזה שליחה חוזרת דורשת אישור מפורש שלכם, כי ייתכן שההודעה כבר נמסרה והלקוח יקבל כפילות. זו מגבלה אמיתית של ספקי הדיוור (אין להם מנגנון מניעת-כפילות מתועד), לא באג.
- אם הכול נכשל תמיד — בדקו במסך המוכנות שהאינטגרציות דוא"ל/SMS ירוקות; אם לא, חסרים מפתחות בסביבת השרת (פעולת תשתית).

## 8. הליך חזרה לאחור (Rollback)

אם פריסה חדשה שוברת משהו:

1. GitHub ← Actions ← Demo Deploy ← Run workflow, ולבחור ב-ref את ה-SHA הקודם שעבד (רשום בכל ריצת deploy קודמת).
2. הפריסה תיכשל אוטומטית אם השרת לא מגיע ל-`ready:true` — כלומר rollback שעבר = מערכת תקינה.
3. אין צורך בשחזור DB: כל שינויי הסכימה אדיטיביים.

## 9. שגרת תפעול יומית (5 דקות)

- [ ] אדמין ← הזמנות: לטפל בהזמנות ממתינות (לאשר/לדחות עם סיבה).
- [ ] פעמון ההתראות: לטפל בהתראות (כולל כשלי מלאי אם יופיעו).
- [ ] עמוד הזמנה שאושרה: לוודא שעדכון הלקוח נשלח (ולנסות שוב אם נכשל).
- [ ] תשלומים שהתקבלו בבנק: לרשום ידנית באדמין ← תשלומים מול החשבונית.

## 10. שגרה שבועית (15 דקות)

- [ ] מסך **מוכנות להפעלה** — לוודא שהכול ירוק.
- [ ] אדמין ← מערכת: בריאות כללית, ריצות עבודות מתוזמנות.
- [ ] GitHub Actions: ריצת Database Backup אחרונה ירוקה; Production Uptime ירוק.
- [ ] אדמין ← מלאי: התאמות מול המחסן הפיזי במידת הצורך.
- [ ] חשבוניות פתוחות מעל שבועיים — מעקב גבייה.

## 11. תקלה: ‎/api/ready לא ירוק

תסמינים: פריסה נכשלת, או שאישורי הזמנות מחזירים שגיאה תפעולית.

1. לקרוא את הסיבה: `curl https://api.crystolia.com/api/ready` (מחזיר `reason` מדויק).
2. **"Database not connected"** — בעיית Atlas/רשת. לבדוק סטטוס Atlas; לרוב חולף.
3. **"does not support transactions"** — בסיס הנתונים אינו replica set. קורה רק אם הוחלף חיבור ה-DB. להחזיר את החיבור ל-Atlas.
4. **"Invoice.order unique index"** — נוצרו חשבוניות כפולות לאותה הזמנה (לא אמור לקרות עם הקוד הנוכחי). לפנות לתמיכה טכנית לניקוי מבוקר; לא למחוק לבד.
5. בכל מקרה: המערכת ממשיכה להגיש דפים ולהציג נתונים; רק אישורי הזמנות/מלאי חסומים עד לתיקון — בכוונה, כדי שלא ייווצר נזק לנתונים.
